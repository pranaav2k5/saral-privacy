# Threat model 0015: record of processing

Status: draft, covers `apps/api/src/ropa`, migration 0013 (`ropa_versions`), and the Records page in `apps/web` (`RopaPage.tsx`, `lib/ropa-form.ts`).

## Scope

The officer or the administrator writes down what the organisation does with personal data and saves it as a numbered version. Versions are kept, read, downloaded as a file and printed. Out of scope: whether the answers are true, whether the reasons an activity is allowed are lawful, any export other than JSON and the browser's print window, and sending the record to anyone.

## Assets

The record itself: it names the organisation's contact person and email, and it describes where data is kept and how it is protected, which is a useful map for an attacker. The integrity of the history, because the record is what the organisation would show an auditor. The audit log, which must not carry the words of the record.

## Trust boundaries

Browser to API (the record travels as JSON in a request with the staff session). API to database (row-level security and a role that can only insert and read). Tenant to tenant.

## Threats

| STRIDE | Threat | Mitigation | Proof |
|---|---|---|---|
| Spoofing, elevation of privilege | A publishable key, a server key or the auditor reads or writes the record. | Every route is for the officer and the administrator only. Nobody without a credential gets 401. | `ropa.e2e.test.ts`: "is for the officer and the administrator only" and the 403 checks of the read routes |
| Information disclosure | One organisation reads another's versions. | Row-level security is enabled and forced on `ropa_versions`, with a policy that also checks writes. A version of another organisation is a 404, never a 403, so its existence is not revealed. | `ropa.test.ts` (DB): "a tenant sees only its own versions"; `ropa.e2e.test.ts`: "another organisation's version is 404" |
| Tampering | A saved version is changed or deleted, to rewrite the history. | The application role has `SELECT` and `INSERT` on the table and nothing else, so neither the API nor a bug in it can change or remove a version. The stored hash must be the hash of the stored text (a CHECK), and a version number is used once. | `ropa.test.ts`: "never change or delete one", "the stored hash must be the hash of the stored text", "a version number is used once" |
| Tampering | A person who owns the database changes a version without anyone seeing. | The audit entry of each save holds the hash of the record, in the tamper-evident chain with its daily anchor. A changed version no longer matches the entry made when it was saved. There is no automatic check that compares the two yet. | `ropa.e2e.test.ts`: "is an audit event holding the hash and none of the words" |
| Tampering | Two people edit from the same version, and the second silently replaces the first's change in the current record. | A save says which version it started from. If another version has been saved since, it is refused (409 `stale`) with the newest number, and the form tells the person. The check is inside the organisation's lock, so two saves at the same moment cannot both succeed. Nothing is lost either way, since every version is kept. | `ropa.e2e.test.ts`: "saying which version a change started from" (including two saves at once); `RopaPage.test.tsx`: the stale refusal |
| Tampering | The history is padded with copies, or hidden among them. | A save that is the same record as the latest version is refused (409 `unchanged`), whatever its note says. The hash is of the canonical text, so the same answers in another key order or spacing are still the same record. | `ropa.e2e.test.ts`: "a save that changes nothing is not a new version"; `ropa-document.test.ts`: canonical form |
| Tampering | A request carries a field that is not part of the record, to store something else or to confuse a later reader. | A key that is not part of the record is refused at every level, as is an unknown key in the request. Texts are trimmed and limited, choices are from fixed lists, countries are two capital letters, the website must be https without a user name or password. | `ropa-document.test.ts`; `ropa.e2e.test.ts`: "refuses a field that is not part of the request" |
| Repudiation | Someone says they did not save a version. | The version keeps who saved it and when, and the save is an audit event (`ropa.version_created`) with the actor and the actor type. | `ropa.e2e.test.ts`: the first test checks `createdBy`; the audit test checks the entry |
| Information disclosure | The words of the record end up in the audit log or in a hash that can be tested for guesses. | The audit entry holds only a hash of the schema, organisation, version number, id and the record's hash. A test reads the entry and finds none of the words. The record is not secret from the organisation, so the hash of its text is not a leak. | `ropa.e2e.test.ts`: "is an audit event holding the hash and none of the words" |
| Information disclosure | The record leaves the browser in a place the person did not choose. | The download is a data address made in the browser and handed to the browser's own download, so no request is made. Print uses the browser's print window. The page makes only the API calls for its own data. | `RopaPage.test.tsx`: the download and print tests |
| Denial of service | A huge record, a huge list or a flood of saves fills the database. | At most 30 activities, bounded lists and texts, at most 90 KiB in canonical text (checked in bytes, and under the API's 100 KB request limit so a larger record is a 400 and not a 413), a database CHECK at 256 KiB, at most 200 versions for an organisation, and the same per-address and per-key rate limits as every route. | `ropa-document.test.ts` and `ropa-form.test.ts`: the size limit to the byte; `ropa.e2e.test.ts`: the 200-version limit and the oversized record |
| Elevation of privilege (cross-site scripting) | A record holds markup, or a website address that runs script, and it is shown to another staff member. | Every value is rendered as text by React. The website must be https, and it is shown as text and never as a link. | `RopaPage.test.tsx`: "markup in a saved record is shown as text and never runs" |
| Misleading assurance | The record is read as legally checked, or an unanswered question is read as "no". | The page says that Saral does not check that the answers are right or the reasons are allowed. The yes and no questions, the reason an activity is allowed and its source start unanswered, "not sure" is an allowed answer, and a hidden country box is ignored when the answer is no. | `RopaPage.test.tsx`: the opening and unanswered-choice tests; `ropa-form.test.ts` |
| Misleading assurance | A review that is overdue is not noticed, or a review is dated after it happened. | The next review is shown in words with the number of days it is overdue. The date of the last review cannot be in the future and the next cannot be before it. | `ropa-form.test.ts`: the review dates and "when the next review is due" |

## Residual risks

- Saral cannot know whether the record is true or complete. An organisation can describe its processing wrongly, and the record will carry its hash and its history all the same. Nothing here reads the organisation's systems.
- The reasons an activity is allowed are chosen by the organisation. Saral offers three answers and does not say whether any of them is right for a given activity. A lawyer or the officer decides.
- The record is a description of where data lives and how it is protected. Anyone who can sign in as the officer or the administrator can read all of it, and a downloaded file is outside Saral's control. Treat it as confidential and keep copies where other confidential documents are kept.
- A person who can write to the database as its owner can still change a version, and only a later check against the audit entry would show it. That check is not built.
- A review that is due or overdue reaches a person who has not opened the dashboard only through the reminder job (threat model 0016), as a webhook event to endpoints that asked for it, and only if the job is run. There is no comparison between two versions, no PDF export (printing to PDF from the browser works), and no import of an existing record.
- A save that started from an old version is refused, but a person who then copies their answers into the newest version by hand can overwrite the other person's meaning without noticing. The history keeps both versions.
- The form and the server check the same rules, in two places, because the form needs the words for each gap and the server must not trust the form. A rule changed in one and not the other shows up as a server refusal in words (`problemsFromRopaError`), not as a wrong save.

Owner of residual risk: repository owner (`pranaav2k5`).
